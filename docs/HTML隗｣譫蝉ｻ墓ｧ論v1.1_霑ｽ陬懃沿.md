# ジモティー監視ツール v1.1 — HTML解析仕様 追補版

本書は「ジモティー監視ツール v1 — HTML解析仕様確定版」（以下 v1.0）に対する
**追補・訂正**をまとめたものである。v1.0は2026-08-22時点でのサンプル1件
（新宿区OA用品カテゴリ、テスト出品者Aの投稿）を根拠にしていたが、
本書は同日に追加検証した以下3ページを根拠に加える。

- 一覧ページ: `https://jmty.jp/tokyo/sale-all/g-all/a-999-shinjuku`（全カテゴリ・242,690件）
- 一覧ページ: `https://jmty.jp/tokyo/sale-pcp/g-1199/a-999-shinjuku`（デスクトップパソコン・275件）
- 個別ページ: `https://jmty.jp/tokyo/sale-pcp/article-1r85k3`（テスト出品者Bの投稿）
- **プロフィールページ: `https://jmty.jp/profiles/678a0accf53550615cb4b528`（v1.0では未検証だった種別）**

取得方法の制約: 本追補版の根拠データはすべて `web_fetch`（Markdown変換済み）
経由であり、生DOMでの検証ではない。CSS構造の妥当性は別途、実行環境での

## 追補1: 一覧ページに「受付終了投稿」ブロックが存在する（v1.0未記載・重要）

一覧ページを最後までスクロールすると、通常の投稿一覧（受付中）の**下に
別ブロック**として「〇〇の受付終了投稿一覧」という見出しが存在し、その中に
取引成立・出品終了した投稿が列挙される。

### 確認できた特徴

- 見出し例: `新宿区のデスクトップパソコン(パソコン)の受付終了投稿一覧`
- 各投稿には `受付終了` というテキストラベルが付与されている
  （例: `ゲーム用PC デスクトップ（pioner COOLER MAST... 受付終了`）
- 受付終了投稿には以下が**表示されない**:
  - お気に入り数（`js_fav_user_count` 相当の表示がない）
  - 「登録済み」等のお気に入りボタン群
  - 一部投稿はサムネイル画像リンクも省略される
- 価格・都道府県・市区町村・駅・カテゴリ・更新日/作成日は通常投稿と同様に表示される
- 広告（alliance-）も受付中・受付終了どちらのブロックにも登場する
  （同一の広告記事が複数の一覧ページに重複出現することも確認）

### 仕様への影響（重要）

v1.0 5-1「一覧から消えた投稿（取引成立・削除と推定）は、バッファテーブルから
自動的に削除する」という設計は、**取引成立した投稿が実際には一覧から消えず、
「受付終了」ブロックに移動して表示され続ける**という事実と矛盾する。

これはローリング監視バッファ設計（仕様書 v1.0 5章）に対する訂正が必要な発見である。
想定される対応（要ユーザー判断）:

- 案A: 受付終了ブロックは**パース対象外**とし、`p-articles-list-item` 相当の
  要素であっても「受付終了」ラベルを持つものは除外する。取引成立の検知は
  従来通り「一覧（受付中ブロック）から消えたら成立とみなす」を維持する。
- 案B: 受付終了ブロックも取り込み、`article_status` フィールド
  （`active` / `closed`）を持たせて明示的に状態管理する。将来的な
  出品者統計（成約率など）に活用できる可能性がある。

**v1では案Aを暫定採用**とする（取得漏れゼロの原則には抵触しない。
受付終了投稿は「新たに監視すべき対象」ではないため）。ただし
受付終了ブロックの投稿は通常ブロックの投稿と**同一のCSSクラスを
共有している可能性がある**ため、パーサー実装時にDOM構造を実機で
確認し、判別方法（親要素の見出しテキストで判定するか、専用クラスの
有無で判定するか）を確定させる必要がある。

## 追補2: 個別ページの日時表示は時刻を含む場合がある（v1.0記載の訂正）

v1.0 14章では「サンプルでは時刻までは表示されていない」「v1では
`2026-08-22` までの精度とする」としていたが、これは**投稿日と閲覧日が
同日だったための見かけ上の制約**だった可能性が高い。

今回の個別ページ（テスト出品者Bの投稿、作成日が閲覧日と異なる）では、
ページ本文に以下の表示が確認された:

```text
更新2026年8月18日 11:49
作成2026年8月17日 23:39
```

### 仕様への影響

- 個別ページ本文（一覧ページの `.p-item-history` とは別の、記事詳細
  ページ上部にある日時表示）には**分単位の時刻が含まれる**。
- 一覧ページ側の `.p-item-history` 表示（「更新8月22日」等）は
  引き続き日付精度のみと考えられる（今回のサンプルでも時刻表示は
  一覧側では確認できなかった）。
- したがって `created_at` / `updated_at` の精度は取得元によって
  異なる: **一覧経由なら日付精度、詳細ページ経由なら分単位精度**。
  DBスキーマ設計時は、どちらの取得元由来かに関わらず単一カラムで
  保持しつつ、精度の違いを許容する（時刻不明な場合は `00:00` 等で
  埋めるか、精度フラグを別途持たせるかは実装時に決定）。

## 追補3: プロフィールページ (`/profiles/{seller_id}`) は単独で豊富な情報を持つ（v1.0未検証）

v1.0では出品者情報を「個別記事ページの投稿者欄」からのみ取得する設計
だったが、プロフィールページ自体に直接アクセスすると、記事詳細ページの
投稿者欄よりも詳細な情報が取得できることが判明した。

### プロフィールページから新たに取得可能と確認できた項目

| 項目 | 記事詳細ページの投稿者欄 | プロフィールページ |
|---|---|---|
| 評価の内訳（良い／普通／悪い） | 合算値のみ（例: `5.0(18)`） | **個別カウント**（良い18・普通0・悪い0） |
| 登録日時 | 取得不可 | **例: `2025/01/17`** |
| 居住区 | 取得不可 | **例: `未登録`**（項目自体は常設） |
| 職業 | 取得不可 | **例: `会社員`** |
| そのユーザーの全投稿一覧 | 不可（詳細ページには「その他の投稿記事」として一部のみ） | **可能。ページネーションあり（`?page=2`等）** |
| 評価コメント全文 | 冒頭2件相当のみ | **全件。タイムスタンプ・評価者プロフィールリンク付き** |
| フォロー機能 | なし | 「＋フォロー」ボタンあり（未ログイン時は誘導のみ） |

プロフィールページのURLパターン:
```text
https://jmty.jp/profiles/{seller_id}
https://jmty.jp/profiles/{seller_id}?page=2          # 投稿一覧の2ページ目
https://jmty.jp/profiles/{seller_id}/evaluations?rating=      # 評価一覧（全件）
https://jmty.jp/profiles/{seller_id}/evaluations?page=2&rating=
```

### 仕様への影響

- 仕様書 v1.0 5-4「良い出品者と判断した場合、その出品者の他の投稿を
  個別ユーザーページ的に閲覧できる導線をUIに用意する」は、
  **プロフィールページへの直リンクを張るだけで実現可能**であり、
  想定より軽い実装で済むことが分かった。
- HTML解析仕様確定版 20章「投稿数」は現在時点のプロフィール表示値で
  あるとされていたが、これは記事詳細ページ経由の値であり、
  **プロフィールページに直接アクセスすればより信頼できる同じ値が
  取得できる**（今回は両者で一致: 投稿15件）。
- v1.0では「詳細ページアクセス回数を抑えるため」評価一覧を対象外に
  していたが、**プロフィールページ自体への直接アクセス1回で
  評価の内訳・登録日時・職業まで一括取得できる**ため、当初懸念していた
  「評価履歴まで見るとアクセス数が増える」という問題は、
  少なくとも「評価の集計値」を見るだけであれば発生しない
  （個々の評価コメント全文を取得する場合は別途 `/evaluations` への
  アクセスが必要になる点は変わらない）。

### 新たに判明した欠損パターン（NGユーザー判定への影響）

評価コメント一覧には以下の欠損状態が存在することを確認した:

- 評価対象の投稿が **`削除済みの投稿です`** と表示されるケース
  （投稿自体は削除されたが評価だけが残る）
- 評価者が **`退会済みユーザー`** と表示され、プロフィールへのリンクが
  存在しないケース

したがって、評価コメントをパースする際は「評価対象投稿URLが存在しない」
「評価者プロフィールURLが存在しない」という2パターンを、エラーではなく
正常系として扱う必要がある。

## 追補4: v1.0からの主要な仕様変更点 一覧（要点まとめ）

| # | v1.0での想定 | 実データでの発見 | 対応方針 |
|---|---|---|---|
| 1 | 一覧から消えたら削除 | 「受付終了」として一覧内に残存する | 受付終了ブロックはパース対象外（暫定） |
| 2 | 日時は日付精度のみ | 詳細ページでは分単位の時刻が付く場合がある | 詳細ページ由来は時刻まで保持可能な設計にする |
| 3 | 出品者情報は詳細ページ経由のみ | プロフィールページ直接アクセスでより多くの情報が取れる | seller_repository は詳細ページ・プロフィールページ両方を情報源として扱う |
| 4 | 評価コメントはv1対象外 | 評価の**集計値**（良い/普通/悪い内訳、登録日、職業）はプロフィールページアクセス1回で取得可能 | v1でもプロフィールページの集計値は取得対象に格上げを検討 |
| 5 | （記載なし） | 評価コメントに「削除済み投稿」「退会済みユーザー」という欠損パターンがある | 評価コメント本文パーサーはこの2パターンをnull許容で設計 |
