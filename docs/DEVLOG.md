## あなたのPCでテストする方法（ここが今回できるようになった一番大きな点）

これまでのパーサー（list/detail/profile）は「HTMLを受け取って解析するだけ」
なので、Anthropicのネットワーク制限とは無関係に、あなたのPCですぐ動きます。
`fetch.py`ができたことで、**実際にジモティーへアクセス→パースまでの
一連の流れ**を初めて通しで確認できます。

```bash
# 1. プロジェクトを展開
cd jimoty-monitor

# 2. 依存パッケージをインストール
pip install -r requirements.txt

# 3. まずユニットテストで現状の実装が壊れていないか確認
python3 -m pytest tests/ -v

# 4. 実際にジモティーへアクセスするエンドツーエンド確認（パーサー単体）
python scripts/manual_e2e_check.py

# 5. 巡回ジョブ本体を1回実行し、DBに実際に保存されるか確認
python scripts/run_scan_once.py

# 6. バックエンドAPIを起動（別ターミナルで）
uvicorn api.main:app --reload --port 8000

# 7. フロントエンドを起動（さらに別ターミナルで）
cd frontend
npm install
npm run dev
```

6・7を両方起動した状態で `http://localhost:5173` を開くと、UIから実際の
投稿一覧・NGワード設定などを操作できます（5で作った`jimoty_monitor.db`を
そのまま読みに行きます）。

**6・7をまとめて起動したい場合**は、直下の`start.bat`（Windows）または
`start.sh`（Mac/Linux）を使うと、バックエンド・フロントエンドを1回の
実行で両方起動できる（2026-08-25 新設）。

```
# Windows: エクスプローラーでダブルクリックするか、コマンドプロンプトで
start.bat

# Mac/Linux
chmod +x start.sh   # 初回のみ
./start.sh
```

いずれも初回は先に`pip install -r requirements.txt`と
`cd frontend && npm install`を済ませておくこと。

`scripts/run_scan_once.py`は`scheduler/job.py`の`run_scan()`を実際に1回
実行し、同じディレクトリに`jimoty_monitor.db`というSQLiteファイルを
作成します（[DB Browser for SQLite](https://sqlitebrowser.org/)等で中身を
確認できます）。同じコマンドをもう一度実行すると、2回目以降は「新規投稿」
の件数が減り、既存投稿の価格変化のみが検知されるはずです。

`scripts/manual_e2e_check.py`は、新宿区パソコンカテゴリの一覧を実際に
取得し、パース結果（件数・先頭3件のタイトルと価格）を表示したあと、
先頭1件の個別ページも取得してパース結果を表示します。これが通れば、
「取得→解析」の基本ルートが動作していることの確認になります。

**2026-08-23、実機（Windows）で動作確認済み。** 一覧取得（50件パース成功）
→個別ページ取得→パース、すべて成功。以下の2点はその過程で判明した
Windows特有のハマりどころ。

- **`python3`ではなく`python`を使うこと**。Windows環境では`python3`という
  コマンド名にMicrosoft Storeのスタブが割り当てられており、何も実行されず
  静かに終了することがある。
- **標準出力を`> result.txt`のようにファイルへリダイレクトすると、
  絵文字を含むタイトル（🉐等、実際の投稿タイトルに頻出する）で
  `UnicodeEncodeError`が発生する**（Windowsのコンソール出力が
  デフォルトでcp932になるため）。`manual_e2e_check.py`側で標準出力を
  UTF-8に強制する対応を入れて解消済み。今後`scheduler/job.py`等で
  ログ出力を実装する際も同様の対応が必要になる。

#### バグ修正：相対URL形式のカテゴリリンクでカテゴリが消失する不具合（2026-08-23）

あなたの実行環境で`scheduler/job.py`を実際に動かし、その結果を
`jimoty_monitor.db`として共有いただいたところ、52件中12件で

想定していなかったため。`scripts/debug_category_loss.py`で実際の
DOM構造を出力してもらい特定した。

`scraper/selectors/url_patterns.py`の`CATEGORY_SLUG_PATTERN`を、
プロトコル・ホスト部分を任意にする形に修正し、あなたが報告した
12件の代表的なDOM構造をそのまま回帰テストとして追加した
（`tests/test_list_parser.py`の末尾4件）。

#### 「一覧から消えた投稿」の扱いについて（重要な設計決定、2026-08-23）

仕様書5-1は「一覧から消えた投稿は自動削除する」としていたが、これは
一覧の固定件数走査という制約上、新着ラッシュで単に圏外に押し出された
だけの投稿を、取引成立と誤判定するリスクを持つ（初回の設計相談時から
指摘していた懸念）。

検討の結果、以下の方式を採用した。

- 一覧から消えた投稿は即削除せず、いったん`missing`状態にする
- `missing`状態の投稿は、次回巡回で個別ページへ直接アクセスして確定判定する
  （新規投稿の詳細取得フロー⑨⑩と同じアクセスパターンを使い回すため、
  実装上の特別扱いはほぼない）
- 判定結果に応じて`active`へ復帰、または削除する

「N回連続で圏外になったら削除」のような多段階カウンタ式の猶予ロジックは
採用しなかった。カウンタが増えるほど目視でのロジック検証が難しくなる、
というユーザーからの懸念を踏まえた判断。代わりに`article_status_history`
テーブルへ「いつ・どの状態から・どの状態に・なぜ変わったか」を都度記録する
方式にしており、動作を後から目視で追いやすい設計にしている。

再浮上時の差分検知は仕様書通り価格変化のみとし、タイトル・説明文の変更は
追跡しない（ユーザーとの合意事項）。

### UI（新規実装）

方針として「バックエンド先行」で進めた。理由は、モックデータでUIを
作ると実データ特有の欠損（`category_name=None`、`price=None`、
サムネイル画像なし等）を想定しないまま組んでしまい、後で手戻りが
発生しやすいため。FastAPIで実データを返すAPIを先に作り、Reactは
最初から実データ（`list_real.html`, `detail_real.html`）で動作確認した。

#### バックエンドAPI (`api/`)

- `api/main.py` — FastAPIサーバー本体。`repository/`層をJSON化して返す薄い層（ビジネスロジックは持たない）
  - `GET /api/articles` — 投稿一覧（`visibility=visible/hidden/all`、`status=active/missing/all`で絞り込み）
  - `GET /api/articles/{id}` — 投稿詳細
  - `GET /api/sellers/{id}`, `GET /api/sellers/{id}/articles` — 出品者情報・その出品者の他投稿（仕様書5-4の導線）
  - `GET/POST/PATCH/DELETE /api/ng-keywords` — NGワードのCRUD＋有効/無効トグル
  - `GET/POST/DELETE /api/ng-categories` — NGカテゴリのCRUD
  - `GET/POST/DELETE /api/seller-rules` — NGユーザー／監視ユーザーのCRUD（`seller_id`重複は409を返す）
  - `POST /api/scan` — `scheduler.job.run_scan()`を実行する「今すぐ更新」ボタン向けエンドポイント
- `tests/test_api.py`（17件）— `TestClient`＋実データで構築したDBに対して主要エンドポイントを検証

起動方法:
```bash
uvicorn api.main:app --reload --port 8000
```
起動後 http://localhost:8000/docs でSwagger UIから直接試せる。

#### 表示モード（カード／リスト／表）について（2026-08-24）

一覧画面はヘッダー右上のアイコンで3モードを切り替えられる。選択状態は
`localStorage`に保存され次回起動時も維持される。ユーザーから「1件ごとの
情報量が多く、スクロールの手間が公式アプリと変わらない」というフィード
バックを受けて追加した。

- **カード**：情報量重視（当初からの実装）
- **リスト**：サムネイル小＋タイトル1行＋価格のみ。1画面に10件以上表示できる
- **表**：PC幅を最大限活かしたExcel風の一覧（画面幅いっぱいに広がる構成に変更、2026-08-24）。カテゴリ/価格帯の絞り込み・列の表示/非表示切り替えに対応。列カスタマイズの選択状態も`localStorage`に保存される（`jimoty-monitor:table-columns`キー）

#### ソートの共通化・公式順の再現（2026-08-24）

「テーブルモードだけソートが独立していて、カード/リストと一貫しない」
「デフォルトが公式サイトの並び順と違う」というフィードバックを受けて
全面的に見直した。

- ソートキー（`display_order`/`last_seen_at`/`price_asc`/`price_desc`）は
  `ArticleListPage`（親コンポーネント）が一元管理し、3表示モードで完全に
  共通。モード切り替えでソート順がリセットされることはない
- **`display_order`**（新設）をデフォルトソートにした。これは
  `scheduler.job.run_scan()`が一覧を取得した際の出現順（`enumerate`）を
  そのまま`active_articles.display_order`に保存したもので、ジモティー
  公式の並び順（PR枠が上位に来る等の特殊ロジックも含む）を再現する
- 選択したソートは`localStorage`（`jimoty-monitor:sort`キー）に保存される

#### カードの複数列表示（2026-08-24）

ヘッダーの「表示列」で1〜4列を選択できる。選択に応じてCSS Gridの列数が
変わる（`jimoty-monitor:card-columns`キーで保存）。当初のカードは画像

#### ウォッチリスト機能（新設、2026-08-24）

「気軽に保存して気軽に消せる」ウォッチリストを実装した。「投稿の監視」
と「ユーザーの監視」の2種類があり、後者は既存の`seller_rules`
（`rule_type='watch'`、設定画面の「監視ユーザー」）とそのまま統合した
（ユーザーとの合意事項：「監視ユーザー」は1つの概念として扱う）。

- **投稿単位のウォッチリスト**：`db/schema.sql`に`watched_articles`

## 重要な発見：仕様書のCSRF/POST方式は「距離指定検索」専用だった

## 重要な設計変更：個別ページ・プロフィールページはクラス名に依存できない

当初、一覧ページと同様に`p-article-detail-table`のような意味のある
CSSクラス名でセレクタを組んでいたが、**実物HTMLを見て判明した事実**として、

- **個別ページ（記事詳細）は意味のあるクラス名が実質ゼロ**。styled-components
  由来のハッシュ化クラス名（例: `sc-a7f3bb80-0 djDmIn`）のみで構成されている。
- **プロフィールページも大部分がハッシュ化クラス**だが、投稿一覧の項目にのみ
  `portal_list_link`という生きたクラス名が残っている。統計情報は`<dt>/<dd>`

見出し語（「商品価格」「ジャンル」「投稿者」等）とDOM位置関係**を頼りに
情報を抽出する設計に変更した。一覧ページ（`p-item-*`等）は生きたクラス名が
豊富に残っているため、従来通りセレクタベースの設計を維持している。

### 実物HTMLをアップロードする際の注意（2026-09-05追記・実例確認済み）

**画像ファイルを含めずに保存すること。** このソフトがHTMLから読み取るのは
`<meta>`タグや本文中の静的なテキスト・構造化データのみで、画像そのもの
（バイナリ）を必要とする処理は一切ない。

2026-09-05に実際に検証したところ、サイズが膨れ上がる主な原因は
**`<img>`タグの`src`属性に画像データそのものがBase64エンコードされて
直接埋め込まれている**ことだった（`src="data:image/jpeg;base64,/9j/...`
のような形式）。ジモティーのサムネイル画像（一覧のサムネイル一覧、
評価コメントの相手アイコン等）がこの方式で埋め込まれており、1枚あたり
数十KB、ページ全体では1つのHTMLファイルが1MB近くになることもある。
パース処理にとってこの画像データは完全に無関係で、転送量とアップロード
時間を無駄に消費するだけである。

保存時は以下のいずれかの方法で、HTML本体のみを保存すること。

- Chrome：保存形式で「ウェブページ、HTMLのみ」を選択する（「ウェブページ、
  完全」は画像等の関連ファイルを同梱してしまうため避ける。ただし
  「HTMLのみ」を選んでもBase64埋め込み画像はHTML自体の一部なので
  除去されない場合がある。まずはこちらを試す）
- 開発者ツールの「Elements」パネルで`<html>`タグを右クリックし
  「Copy → Copy outerHTML」でクリップボードにコピーし、テキストファイル
  として保存する方法（同上の理由でBase64画像が残る場合がある）
- **上記でもファイルサイズが大きい場合**：テキストエディタで開き、
  `data:image/`という文字列を検索し、その行（`<img ... src="data:image/
  ...">`のような1つのタグ）を`src`属性の中身だけ`src="(省略)"`のように
  置き換えて保存する。少し手間はかかるが、最も確実にサイズを削減できる。
  このソフトのパース対象は`<meta>`タグや本文テキストであり、`<img>`タグの
  `src`の中身自体は使わないため、この編集をしても解析結果に影響しない。

なお、いずれの保存方法でも、JavaScriptによって後から動的に挿入される
要素（画像ギャラリー等、ページ読み込み後にAPIから取得されるもの）は
再現されない点に注意。あくまで「ページ読み込み直後の静的なHTML構造」の
みが対象。

## 出品者紹介文の根本的な取得元の見直し（2026-08-28、追加調査）

前回「`direct_texts[0]`しか見ていなかったため紹介文が切り詰められていた」

## 設計変更：巡回時自動取得の撤回 → 「見るまでは取らない」遅延取得方式（2026-08-30）

上記「巡回時にプロフィールページも自動取得する」実装は、**ユーザー合意の
もと撤回し、以下の遅延取得方式に置き換えた**。このセクションが最新の
仕様。上記の「出品者紹介文の根本的な取得元の見直し」セクションは経緯と
して残すが、そこに書かれた「新規投稿1件あたり個別ページ1回＋プロフィール
ページ1回」という挙動はもう存在しない。

### 変更理由

巡回のたびに新規出品者のプロフィールページへ機械的にアクセスするのは、
低頻度アクセスの原則には反しないものの、ユーザーにとってもジモティー側
にとっても不要なアクセスを増やす（ユーザーがそのプロフィールを一度も
見ないまま終わる場合が多いため）。「実際に見るときにだけ取得する」方が
より低負荷という判断で設計変更した。

### 新しい設計

- **巡回時（`run_scan`）**：プロフィールページへの追加アクセスは行わない
  （`_fetch_and_store_detail()`から自動取得処理・`fetched_seller_profile_ids`
  を撤回し、元の「個別ページ取得→出品者登録のみ」の姿に戻した）
- **出品者パネルを開いたとき**：DB内にある情報（個別ページ由来、省略され
  ている可能性あり）をそのまま表示
- **「続きを読む」を押したとき**：`sellers.profile_fetched_at`が未取得
  （NULL）であれば、その場でプロフィールページを取得して全文を反映。
  以後はDBに保存されるので再取得しない。紹介文が短く省略の必要がない
  出品者は、そもそも「続きを読む」ボタンが出ないため、「更新」ボタンを
  押さない限りプロフィールは未取得のまま（意図した挙動）
- **「更新」ボタン（新設）**：`profile_fetched_at`の状態に関わらず必ず
  プロフィールページを再取得し、評価数・投稿数・紹介文などを最新化する。
  初回に限れば「続きを読む」と全く同じ挙動になる

### 実装

- `db/schema.sql`：`sellers`テーブルに`profile_fetched_at TEXT`カラムを
  追加（プロフィールページを最後に取得した時刻。未取得ならNULL）
- `repository/seller_repository.py`：`upsert_seller_profile()`が
  `profile_fetched_at = datetime('now')`も記録するようにした
- `scheduler/job.py`：`_fetch_and_store_detail()`からプロフィール自動
  取得処理を撤回。新関数`fetch_seller_profile_on_demand(conn, client,
  seller_id)`を追加（出品者のプロフィールページを無条件で取得しDBを
  更新する。呼び出し元が「続きを読む」／「更新」の判定を行う）
- `api/main.py`：`POST /api/sellers/{seller_id}/fetch-profile`エンド
  ポイントを新設。`fetch_seller_profile_on_demand()`を呼ぶ薄いラッパー。
  出品者が存在しなければ404、取得失敗なら502
- `frontend/src/api/client.js`：`fetchSellerProfile(sellerId)`を追加
- `frontend/src/components/SellerPanel.jsx`：
  - 「続きを読む」（`handleReadMore`）：`profile_fetched_at`がnullなら
    `doFetchProfile()`を先に呼んでから展開。取得済みなら即展開のみ
  - 「更新」ボタン（新設、`handleRefresh`）：常に`doFetchProfile()`を呼ぶ
  - `doFetchProfile()`：`api.fetchSellerProfile()`を呼び、成功なら
    `setSeller(updated)`、失敗なら`profileFetchError`にメッセージを保持
  - ローディング状態`profileFetching`、「プロフィール最終更新: ...」の
    表示を追加

### 懸念点として検討済みの事項

- 「更新」ボタンを押した瞬間にHTTPリクエストが発生するため応答が遅くなる
  （体感1秒前後）。ローディング表示必須（対応済み）
- 取得失敗時に「更新しました」と嘘をつかないよう、必ず成功/失敗を待つ
  同期処理にしている（対応済み）
- 同じ出品者を複数タブ・複数投稿から同時に「続きを読む」された場合、
  理論上同時に2回プロフィール取得が走りうるが、両方とも同じ内容で
  上書きするだけなので実害なしと判断し許容
- `last_updated_at`とは別に`profile_fetched_at`をUIに出すことで、
  出品者パネルを見た人が「これはいつの情報か」を把握できるようにした

## バグ修正：出品者の「他の投稿」件数がページ送り未対応で中途半端になる不具合（2026-09-04）

## 設計変更：プロフィールページの複数ページ取得を撤回（2026-09-04）

### 背景

直前のセクションで、プロフィールページの投稿一覧が11件以上ある場合に
`next_page_url`を辿って全ページ合算する実装を入れた
（`MAX_PROFILE_PAGES = 20`）。

しかしこれは「監視ユーザーに登録した出品者の投稿は全部見たい」という
自然な要望と、「巡回は地域一覧のトップ1ページのみ、低頻度アクセスの
原則」という当初からの設計方針が噛み合っていない状態で足された実装
だった。恒常的に数百件規模の出品を抱える出品者では、「更新」ボタン
1回につき最大20回のアクセスが発生しうる。これは「1日数回・トップ1
ページのみ」というユーザーとジモティー運営への問い合わせに基づく
合意条件（README冒頭・設計上の留意点）に実質的に反する。

### 論点の整理（この方針転換の判断材料）

- **一覧巡回（`run_scan`）とプロフィール取得は別物**。一覧巡回は今後も
  常に1ページのみで変更しない。「監視ユーザーに登録したら新規投稿を
  自動で追いかけたい」という要望も、一覧巡回を複数ページ化したり
  監視ユーザーのプロフィールを巡回のたびに自動取得したりする形では
  対応しない（アクセス数が監視人数に比例して増えるため）。
- プロフィールページの取得は、ユーザーが「続きを読む」または「更新」
  を明示的に押した時に限られる（「見るまでは取らない」設計、
  2026-08-30）。この「1回のトリガーで何ページ取得するか」の部分だけが
  今回の見直し対象。
- 出品者によっては恒常的に数百件の投稿が生きているケースがあり、
  「全件を毎回取得する」設計は開発環境の想定より実運用での負荷が
  大きくなりやすい。

### 決定事項

- プロフィールページの取得は **常に1ページ目のみ** とする
  （`next_page_url`は辿らない）。1出品者につき「更新」1回で追加
  アクセス1回、という当初の原則に戻す。
- 合計出品数（「今何件出品しているか」）は、1ページ目の「全◯件中」
  という表記（`other_articles_total_count`）から取得できるため、
  複数ページ辿らなくても正確に分かる。この値は`sellers.post_count`
  として引き続き保存する（終了済みの投稿も合算されている可能性が
  あるが、実用上は許容する）。
- 「どんな商品を出しているか」は1ページ目（最終更新日順で最大10件
  程度）の概観が見られれば十分とし、全件の一覧化は目的としない。
  このソフトはログインも問い合わせもせず、ジモティー公式サイト上での
  実際のやり取りを補助する監視・概覧ツールという位置付けであるため、
  この妥協は設計思想と整合する。

### 実装内容

- `scheduler/job.py`：`fetch_seller_profile_on_demand()`から
  `next_page_url`を辿るwhileループと`MAX_PROFILE_PAGES`を削除。
  1ページ目のパース結果をそのまま保存する。
- `scraper/profile_parser.py`：`ProfileInfo.next_page_url`は
  パース結果としては引き続き保持するが、呼び出し元では使用しない旨を
  コメントに明記（値自体の抽出ロジックは変更なし。将来UIで「次ページ
  へのリンク」を出す等の用途に使う可能性は残している）。
- `frontend/src/components/SellerPanel.jsx`：「この出品者の他の投稿」
  見出しを、合計出品数と実際の表示件数を分けて示す表現に変更した
  （例：「全30件中 10件を表示」）。表示件数が合計より少ない場合は、
  「残り◯件は表示していません。全件確認するには公式サイトをご覧
  ください」という注記を追加した。

（`test_fetch_seller_profile_on_demand_follows_pagination`、

## 設計変更：run_missing_check()の廃止と「公開終了」タブの新設（2026-09-04）

### 背景

DBの肥大化とアクセス数についてユーザーと議論した結果、2つの懸念が
浮かび上がった。

1. `active_articles`は1行あたり約9.7KB（全文説明等の44列）と重く、
   `run_missing_check()`（一覧から消えた投稿を毎回自動で個別ページ
   確認するバルク処理、2026-08-23設計）を運用しない限り、削除される
   投稿が無いため肥大化し続ける（実測ベースの試算で年間100MB超）
2. 一方で`run_missing_check()`を定期運用すると、missing状態の投稿
   全件に個別ページアクセスが発生し、巡回のアクセス数が実質倍増
   しうる。「1日数回・トップ1ページのみ」という当初合意していた
   低頻度アクセスの原則と相反する

### ジモティーの性質に合わせたコンセプト（ユーザーとの合意事項）

「新着投稿から掘り出し物を探す」という当初の目的に立ち返ると、
ジモティーには以下の性質がある。

- 良品はすぐに取引終了になる（長く生き残る投稿は少ない）
- 価格更新や再投稿があれば、一覧の上位に自然に再出現する
- 3週間以上前の投稿まで保持・監視し続ける必要は薄い

この性質を踏まえ、「一覧から消えた投稿を毎回自動で確認しに行く」
精度重視の設計から、「ユーザーが興味を持った投稿だけ個別に確認し、
それ以外は一定期間で自動的に整理する」シンプルさ重視の設計に
方針転換した。

### 新しい設計

- **`run_missing_check()`（バルク版）を廃止**。巡回ジョブから
  missing投稿全件へ自動アクセスする経路を撤去した
- 一覧から消えた投稿は、これまで通り`missing`状態としてマークする
  （`run_scan()`の`mark_missing_articles()`はそのまま維持）。ただし
  以後は自動で確認しには行かない
- フロントエンドに**「公開中」「公開終了」タブ**を新設。「公開終了」
  タブでは`missing`状態の投稿が一覧表示される。「これは人気な出品
  だったのかもしれない」という参考情報として、掲載期間（初回確認〜
  公開終了までの日数）も表示する
- 「公開終了」タブの各投稿には**「確認」ボタン**があり、ユーザーが
  興味を持った投稿だけ、押した時にその場で個別ページへアクセスして
  確定判定する（`confirm_single_missing_article()`、1件単位）。
  まだ受付中(`restored`)なら自動的に「公開中」タブに戻り、本当に
  終了(`deleted`)していれば投稿ごと削除される
- **保持期限バッチ**：`missing`になってから3週間（既定、
  `missing_since`起点）経過し、かつユーザーが確認しなかった投稿は、
  `purge_expired_missing_articles()`が自動的に削除する。この処理は
  DB内で完結し、外部への一切のHTTPアクセスを伴わないため、
  `run_scan()`の一環として毎回実行しても低頻度アクセスの原則に
  反しない。「一覧に見え続けている限りは残る」設計（起点を
  `first_seen_at`ではなく`missing_since`にした理由）

### 実装

- `repository/article_repository.py`：`purge_expired_missing_articles()`
  を新設
- `scheduler/job.py`：
  - `run_missing_check()`を削除し、`confirm_single_missing_article()`
    （1件単位）に置き換え
  - `run_scan()`の一環として`purge_expired_missing_articles()`を
    呼ぶようにした
  - `ScanResult`に`purged_count`を追加
- `api/main.py`：
  - `POST /api/articles/{article_id}/confirm-status`を新設
  - `ArticleOut`に`missing_since`を追加（「公開終了」タブの掲載期間
    表示用）
  - `GET /api/articles`の`status`パラメータ（`active`/`missing`/`all`、
    実は2026-08-23の初期設計時点で既に実装済みだった）を活用
- `frontend/src/components/ClosedArticleCard.jsx`：新規作成。
  「公開中」の`ArticleCard`とはあえてレイアウトを分離した専用カード。
  価格・写真より「初回確認」「公開終了」「掲載期間」を主役にした

## 追加バグ修正（2026-08-28）

### 出品者の自己紹介文が最初の1文で切り詰められる不具合

`detail_parser.py`の紹介文抽出が`direct_texts[0]`（要素直下の最初の
テキストノードのみ）を採用していたため、紹介文が改行や`<br>`等で
複数のテキストノードに分かれている場合、最初の1文だけを拾って
残りを切り捨てていた。「続きを読む」を押しても全文が表示されない、
というユーザー報告で発覚（前回のセッションでは「続きを読むボタン自体は

候補となる要素が見つかった時点で`el.get_text(separator="\n", strip=True)`
を使い、要素内の全テキストを結合して紹介文として採用するよう修正した。
`tests/test_detail_parser.py`に複数行紹介文の回帰テストを追加。

### テーブルモードでNGメニューが画面外にはみ出る不具合

`NgButton.jsx`のポップオーバーメニューが常に`right-0`固定（ボタンの
右端に揃えて左方向に開く）だったため、テーブルモードで画面左寄りの
行にあるNGボタンを押すと、メニューが画面外（テーブルの外）にはみ出して
見切れていた。ボタンの`getBoundingClientRect()`で画面上の位置を取得し、
左側に十分なスペース（メニュー幅224px）がない場合は右方向に開く
（`left-0`）よう自動判定するようにした。

  （visible/hidden/all）の組み合わせをタブごとに固定値として持つ。
- `監視`タブは、従来別々だった「監視投稿」（投稿単位、`watchlist`
  テーブル）と「監視ユーザー」（出品者単位、`seller_rules.rule_type
  ='watch'`）の**表示だけ**を1つに統合した。

### バックエンド：`visibility=watched_all`の新設

`GET /api/articles`の`visibility`パラメータに`watched_all`を追加。
`watched`（投稿単位）と`watched_sellers`（出品者単位）のOR条件で
返す。既存の`watched`・`watched_sellers`は後方互換のためそのまま
残している。

**設計判断**：投稿単位の監視（気軽に保存して気軽に消せるもの）と
出品者単位の監視（設定画面で明示的に管理するもの）は、意図的に
別テーブル・別ライフサイクルで設計されていた（2026-08-24, 08-26
合意事項）。この区別を壊さないよう、統合するのは表示のみとし、
データ構造・操作系（☆ボタンでの個別解除、SellerPanelの監視解除
ボタン、設定画面での一覧管理）はすべて従来通り独立させたまま
残した。

これに伴い、「すべて解除」ボタン（旧:監視投稿タブ専用）は統合後の
「監視」タブでも**投稿単位の監視のみ**を対象とする（ボタン文言を
「投稿の監視を解除」に変更し、確認ダイアログにも「監視ユーザー登録
は解除されません」と明記した）。監視ユーザーの解除まで一括で行うと、
誤操作で出品者の監視登録が意図せず消えるリスクがあるため、あえて
範囲を広げなかった。

### バックエンド：カテゴリ候補サジェストAPIの新設

`GET /api/categories/used`を新設。`active_articles`テーブルに
実際に保存されている投稿から、出現済みの`category_id`・
`category_mid_id`（中間カテゴリ）とその名前をDISTINCTで抽出して
返す。

**設計判断**：ジモティー側にカテゴリ一覧を取得できるAPIが存在しない
ため、完全なカテゴリマスタは持てない。しかし「このソフトが実際に
監視してきた投稿が使っているカテゴリ」であれば確実に取得でき、
実用上はこれで十分と判断した（ユーザーが実際に見た投稿からNGに

登録可能。

`SettingsPage.jsx`のNGカテゴリ入力欄の下に、登録済みでない候補を

反映されるだけで、実際の登録は「＋」ボタンを押すまで行わない
(誤クリックでの即時登録を防ぐため)。

## UI改善第3弾・重要バグ修正：フィルタフラグの即時反映（2026-09-05）

### 背景

ユーザーからのスクリーンショット付きフィードバックを受けて、以下4点を
修正した。

1. リストモードで価格・出品者名が横並び1行だったため、価格の桁数や
   出品者名の長さによって見た目が揃わない
2. 「NG」タブと「監視」タブが同じ表示に見えるという報告
3. NGワード・NGカテゴリ・NGユーザーを登録した直後、一覧に反映されない
4. テーブルモードで監視/NGボタンの右側に不要な空白が残っている

### 2と3は同一の根本原因だった（重要）

調査の結果、2は3が引き起こした見え方の問題だったと判明した。

`is_hidden_by_keyword`・`is_hidden_by_category`・
`is_hidden_by_seller_rule`の3フラグは、従来
`scheduler/job.py`の`run_scan()`（巡回処理）の中でしか再計算されて
いなかった。このため、NGユーザーを登録しても、次に「今すぐ更新」を
押すまでの間、既存のDB内投稿のフラグは古いまま（NG登録前の状態）
だった。

ユーザーが実際に見ていたのは「NGユーザー登録した直後、その投稿が
NG判定がまだ効いておらず『フィルタ』タブに残ったままだった」という
状態であり、「NGタブと監視タブが同じ表示になった」というのは
この遅延を誤認した結果だった。バックエンド側のクエリロジック自体
（`visibility=hidden`と`visibility=watched_all`）は独立して正しく
動作していることを、実際にAPIを呼び出して確認済み。

### 実装内容（3・2の修正）

- `filters/recompute.py`を新設。`active_articles`全件に対して
  NGワード・NGカテゴリ・NGユーザー判定を再実行し、フラグが変化した
  行だけをUPDATEする`recompute_all_filter_flags()`を実装した。
- NGワード・NGカテゴリ・seller_rulesの登録・削除・有効無効切替を行う
  全6エンドポイント（`POST/DELETE /ng-keywords`、
  `PATCH /ng-keywords/{id}/toggle`、`POST/DELETE /ng-categories`、
  `POST/DELETE /seller-rules`）から、コミット直後にこの関数を
  呼び出すようにした。
- この再計算はDB内で完結し、ネットワークアクセスは一切発生しない
  ため、低頻度アクセスの原則には抵触しない。
- `scheduler/job.py`の`_load_active_rules()`と同じロジックを
  `filters/recompute.py`内に複製した（循環import回避のため独立させた。
  巡回処理側の既存動作に影響を与えないための判断）。

### 実装内容（1の修正）

- `ArticleRow.jsx`（リストモード）で、価格・出品者名を右寄せの
  縦積み（上：価格、下：出品者名）に変更した。これにより価格の
  桁数や出品者名の長さに関わらず、右端が常に揃うようになった。

### 実装内容（4の修正）

- `ArticleTable.jsx`のサムネイル+監視/NGボタン列の幅を、
  以前は`thumbnailPx + 56`という固定の上乗せ値だったのを、
  ボタン部分の実際の必要幅（アイコン2つ分+gap+セルパディング）から
  計算する方式に変更した。サムネイルサイズを変えても、余白が
  不自然に広がったり狭まったりしなくなった。

### テスト追加

`tests/test_api.py`に5件追加：
- NGワード登録直後に投稿が即座に非表示側へ移ること
- NGワード削除直後に即座に表示側へ戻ること

## UI改善第4弾・設定画面の並び順修正（2026-09-05）

### 背景

ユーザーからの追加フィードバックを受けて以下3点を修正した。

1. テーブルモード共通ヘッダーで、「サムネイルサイズ」の位置が
   リストモードとテーブルモードで変わって見える
2. テーブルモードの監視/NGボタンの右側に、修正後もまだ余白が
   残っていた
3. 設定画面のユーザー一覧（NG/監視）が登録順のまま混在しており、
   種別ごとにまとまっていない

### 1. サムネイルサイズの位置ズレ

「列の境界をドラッグ〜」の注意書きと「列」選択ボタンは表モード固有の
要素で、以前はサムネイルサイズの右側に置いていた。このため、リスト
モード（テーブル固有の要素がない）からテーブルモードに切り替えると、
共通要素であるサムネイルサイズの位置が相対的にずれて見えていた。
表モード固有の要素を先に、リスト・テーブル共通のサムネイルサイズを
常に表示モード切替ボタンの直前（一番右寄り）に配置する順序に変更し、
モードを切り替えてもサムネイルサイズの位置が変わらないようにした。

### 2. テーブルモードの右側の余白（2026-09-05時点、後に問題判明）

前回、サムネイル+監視/NGボタン列の幅を「ボタンの実際の必要幅を計算
した固定px」に変更したが、見積もり値と実際の描画幅がずれており、
余白が解消しきれていなかった。この時点では、固定pxを見積もる方式
自体を撤回し、`table-layout: fixed`下でも列を中身にぴったり合わせる
慣用テクニック（列幅を`0.1%`に指定し、セルに`white-space: nowrap`を
組み合わせる）に変更した。

**→ この対応は2026-09-06に別の不具合（サムネイルへのボタン重なり）
を引き起こしたため撤回した。詳細は次節「UI改善第5弾」を参照。**

### 3. 設定画面のユーザー一覧の並び順

`GET /api/seller-rules?rule_type=all`のソート順を`id DESC`（登録順の
新しい順、種別問わず）から`rule_type ASC, id DESC`に変更した。
`rule_type`の値が`'ng'`と`'watch'`で、アルファベット順で`'ng'`が
先に来ることを利用し、「NGユーザー全員（その中で登録が新しい順）→
監視ユーザー全員（その中で登録が新しい順）」の順で常に表示される
ようにした。

### テスト追加

`tests/test_api.py`に1件追加：意図的に監視→NG→監視→NGの順で登録し、
それでも常にNG全員→監視全員の順で返ることを確認するテスト。

バックエンド全テスト：196件全通過。フロントエンドビルド・lint：成功。

## UI改善第5弾：サムネイル侵食バグの修正（2026-09-06）

### 背景

前節「UI改善第4弾」の2番で採用した`width: "0.1%"` + `white-space:
nowrap`という列幅の慣用テクニックは、単一のテキストセルには有効
だが、「サムネイル画像 + 監視/NGボタン」という`flex`レイアウトを
含む複合コンテンツには不向きだった。サムネイルサイズをどの設定
（小・中・大）にしても、監視/NGボタンがサムネイル画像の上に重なって
表示される不具合が発生した（ユーザー添付のスクリーンショットで確認）。

`table-layout: fixed`下で`0.1%`のような極小値を指定すると、ブラウザは
「最小限まで縮める」という指示として扱うが、flexコンテナを含む複合
コンテンツでは中身の実際の必要幅（`min-content`）を正しく再計算せず、
セルの実際の幅が中身より狭くなり、はみ出た要素が隣接要素に重なって
描画される場合があった。

### 実装内容

`ArticleTable.jsx`の列幅計算を、「中身にぴったり合わせるテクニック」
から「固定pxを正確に積み上げて計算する」方式に戻した。以前
（2026-09-05時点）の同様の対応と異なるのは、今回は見積もりの内訳

## 重要バグ修正：個別ページ処理中の例外で巡回全体が停止する不具合（2026-09-06）

### 背景

ユーザーからの報告「投稿詳細ページで投稿日・最終更新日が表示されない」
を調査した結果、当初は「個別ページ未取得の投稿では表示されないのは
仕様通り」という説明をしたが、「最初の巡回で全投稿の個別ページを
取得しているはずなのに、直後に開いても表示されないのはおかしい」と
再指摘を受け、再調査で重大な設計上の欠陥を発見した。

### 発見した問題

`scheduler/job.py`の`_fetch_and_store_detail()`は、ネットワークエラー
（`FetchError`）しか捕捉しておらず、`parse_detail_page()`のパース
失敗・`article_id`抽出失敗（`ValueError`）・想定外のDBエラー等、
それ以外のあらゆる例外を一切捕捉していなかった。

このため、一覧に52件の投稿があるうち、たまたま1件でも個別ページの
取得・パースで例外が発生すると、その例外が`run_scan()`の`for`ループを
突き抜けて巡回処理全体を中断させていた。一覧由来のデータ（タイトル・
価格など）は先に保存済みのため投稿自体は一覧に表示されるが、それ
以降に処理されるはずだった投稿の個別ページ情報（投稿日・更新日・
出品者情報等）が軒並み欠落する、という気づきにくい形で症状が出て
いた。実際に検証用スクリプトで再現したところ、52件中51件の
`created_datetime`・`updated_datetime`・`detail_fetched_at`が全て
NULLのまま保存されていた。

副次的な問題として、`upsert_from_detail_article()`が
`detail.article_id`（詳細ページ側でパースしたID）だけを頼りに
UPDATE対象の行を決めていたことも発見した。一覧側の`article_id`と
詳細ページ側でパースした`article_id`が食い違った場合、該当行が
見つからずUPDATEが静かに0件で終わる（＝取得したのに保存されない）
リスクがあった。

### 実装内容

- `scheduler/job.py`：`_fetch_and_store_detail()`の`try/except`の
  範囲を、`fetch_html`だけでなく`parse_detail_page`・`upsert_seller`・
  `upsert_from_detail_article`まで含む形に広げた。`FetchError`は
  従来通り個別のログメッセージで扱い、それ以外の例外は
  `logger.exception()`でスタックトレース付きログを残した上で、
  その投稿の処理だけを打ち切り、次の投稿の処理に進む（仕様書5-4
  「取得漏れゼロの原則」に沿った修正）。
- `repository/article_repository.py`：`upsert_from_detail_article()`
  に`article_id`引数（キーワード専用、省略時は従来通り
  `detail.article_id`を使う後方互換）を追加した。呼び出し元
  （`_fetch_and_store_detail`）は一覧側で確定済みの`article_id`を
  明示的に渡すようにし、詳細ページ側のパース結果に依存せず確実に
  正しい行を更新できるようにした。
- `_fetch_and_store_detail()`内で、一覧側`article_id`と詳細ページ側
  `article_id`が食い違う場合に警告ログを出すようにした（今後同種の
  問題が起きた際に、ログから早期発見できるようにするため）。

### テスト追加

`tests/test_scheduler_job.py`に2件追加：
- 個別ページ処理中に例外が発生しても、`run_scan()`全体は中断せず、
  一覧52件全件が保存されること（意図的に最初の3件で例外を発生させて
  検証）
- 一覧側と詳細ページ側の`article_id`が食い違う場合に警告ログが
  出ること

バックエンド全テスト：198件全通過。フロントエンドビルド・lint：
影響なし（変更対象外だが確認済み）。

### 教訓（今後のコードレビューで意識すべき点）

「例外を握りつぶさない」という原則と「1件の失敗が全体を止めない」
という原則は、どちらか一方だけでは不十分で、両方が必要だった。
今回は後者が欠けていたために、一見動いているように見えても
（巡回自体はエラーなく完走したように見えても）、実際には多くの
投稿でデータが欠落するという静かな不具合になっていた。ループ内で
外部リソース（HTTPリクエスト、HTMLパース）を扱う処理は、想定外の
例外が起きても他の要素の処理を継続できるよう、常にtry/exceptで
1件単位に閉じ込めることを徹底する。

## UI改善第6弾：テーブル列幅の根本原因を特定・修正（2026-09-06）

### 背景

前回（UI改善第5弾）でサムネイル侵食バグを修正したところ、ユーザーから
「侵食は直ったが、監視/NGボタン列の右側の余白がまだ残っている。
なぜ詰められないのか」という核心的な指摘を受けた。表面的な列幅の
再計算を繰り返すのではなく、`table-layout: fixed`のCSS仕様そのものを
調査し直した。

### 根本原因（CSS仕様の調査で判明）

`table-layout: fixed`は、列幅の合計がテーブルの`width`（今回は
`100%`）に届かない場合、その差分をブラウザ実装依存の規則でどこかの
列に配分するという仕様がある。`TABLE_COLUMNS`の全列
（サムネイル・タイトル・価格・出品者・カテゴリ・地域・お気に入り・
最終確認）に固定の`defaultWidth`を指定していたため、「余った幅を
吸収する列」が1つも存在しなかった。多くの環境ではこの余りが意図せず
**最初の列**（サムネイル+監視/NGボタン列）に配分されてしまい、
右側の空白として見えていた。

前回・前々回の対応（固定pxの見積もり、`width: 0.1%`の慣用テクニック）
は、いずれも「サムネイル列自体の幅計算」を対象にしていたが、実際の
原因は「他のどの列も伸縮しないため、余りが行き場を失ってサムネイル
列に押し付けられていた」ことだった。列単体の幅計算をいくら精緻化
しても、原理的に解決しない問題だった。

### 実装内容

- `ArticleTable.jsx`：タイトル列（`alwaysOn`の列）だけ`colgroup`の
  `<col>`要素に`width`を指定しないようにした。`table-layout: fixed`
  の仕様上、幅未指定の列は「残りの幅を全て受け取る」役割になるため、
  余白は常にタイトル列に吸収されるようになり、サムネイル・価格・
  出品者等の固定幅列は指定した幅から一切ずれなくなった。
- タイトル列は、ドラッグリサイズ・ダブルクリック自動調整の対象からも
  外した。`col`側で幅指定を無視する設計にした以上、これらの操作が
  効かないため、UIとして触れるハンドル自体を出さないようにした。
- `<th>`の先頭空セルのパディング（`px-2`）を、対応する`<td>`
  （`px-1.5`）と揃えた。ヘッダー行とボディ行でパディングが食い違うと
  列幅計算にズレが生じるため。

### 教訓

CSSの見た目の不具合は、個々の要素の値を調整するより先に、レイアウト
アルゴリズム全体の仕様（今回は`table-layout: fixed`の列幅配分規則）
を確認すべきだった。同じ症状に対して3回連続で対症療法的な修正を
繰り返してしまったのは、原因の切り分けが不十分だったため。

### 未検証（実機確認が必要）

- サムネイルサイズ「小・中・大」いずれでも、監視/NGボタン列の右側に
  余白が残らないこと
- タイトル列の幅がウィンドウサイズに応じて伸縮し、他の列は固定幅の
  まま保たれること

## 調査続報：投稿日抽出が実機の巡回では全件失敗している（2026-09-07）

### 判明した事実

前回追加した診断ログにより、ユーザーの実機ログを確認したところ、
**巡回で処理された投稿すべてで`history_datetimes={}`（空）**という

DB更新自体は正常に行われている。つまり「一部の投稿だけ失敗する」

日付抽出ロジックが常に空を返している**ことが確定した。

一方、ユーザーが同じ投稿をブラウザで直接開いて確認したところ、
「作成2026年9月7日 09:28」という表示が実際に存在していた

- ジモティー側のページには投稿日情報が存在する

という可能性である。ただし現時点では未確認であり、あくまで最有力の
仮説に留まる。

## 2026-09-07：バグ4件の修正 + 取得範囲設定・タイトル更新反映の追加

ユーザーから提供された実際の巡回取得HTML（デバッグ機能で保存された、
東京都新宿区「フェルトブーツ」投稿のページ。以下「今回のサンプル」）
を精査した結果、以前から気づかれていた「投稿日・更新日が表示されない」
不具合の原因が判明し、さらに調査を広げたところ追加で3件のバグが
見つかった。あわせて、都道府県・市区町村・マイエリアの選択機能や
取得範囲設定を見据えた足元固めとして、以下の新機能も実装した。

### バグ修正1：Reactコメントノードによるテキスト分断で投稿日・更新日が取得できない

**症状**：個別ページの「投稿日」「最終更新日」が常に空になる。

**原因**：`scraper/detail_parser.py`の`history_datetimes`抽出処理が
`soup.find_all(string=re.compile(r"(更新|作成)\d{4}年"))`のように、
正規表現を**個々のテキストノード単体**に対して評価していた。
しかし実際の巡回取得HTMLには

```html
<div>作成<!-- -->2026年9月7日 09:17</div>
```

のように、Reactのハイドレーション用コメント（中身は空）が「作成」と
日付本体の間に挟まっているケースが存在する。BeautifulSoup上で
`Comment`は`NavigableString`のサブクラスだが、`find_all(string=...)`は
テキストノードごとに独立して正規表現を評価するため、「作成」だけの
断片と「2026年...」だけの断片に分かれてしまい、どちらも単独では
パターンに一致しない。

なお、既存のテストフィクスチャ（`detail_real.html`等3つ）はこの
コメント分断がない状態で保存されており、実際の巡回取得HTMLとの
乖離があったため、これまでのテストでは検出できていなかった。

**修正内容**：`_find_history_datetimes()`を新設。「更新」または
「作成」を含むテキストノードの**親要素**の`get_text()`（子孫の
コメントノードは自動的に無視され、複数テキストノードは連結される）
に対して正規表現を適用する方式に変更した。コメントで分断されている
場合・されていない場合の両方に対応する。

今回のサンプル（`1rnjaf.html`）を`tests/fixtures/detail_real3_comment_split.html`
として追加し、回帰テストの対象にした。

### バグ修正2：カテゴリによってBreadcrumbListの階層数が異なり、都道府県名の抽出に失敗する

**症状**：一部のカテゴリ（例：「靴/バッグ」）の投稿で`prefecture`が
`null`になり、`category_parent_name`等も本来とは異なる階層の値を
拾ってしまう。

**原因**：`_parse_breadcrumb_json_ld()`がBreadcrumbList JSON-LDの
`position`番号を固定で決め打ちしていた（`position==3`を親カテゴリ、
`position==5`を県名、という具合）。しかし実データ検証の結果、
カテゴリによって階層数そのものが異なることが判明した：

```
パソコン:   ジモティー/売ります・あげます/パソコン/OA用品/
            東京都のOA用品/新宿区のOA用品/(投稿タイトル)   → 全7階層
靴/バッグ:  ジモティー/売ります・あげます/靴/バッグ/靴/ブーツ/
            東京都のブーツ/新宿区のブーツ/(投稿タイトル)   → 全8階層
生活雑貨:   ジモティー/売ります・あげます/生活雑貨/調理器具/
            鍋、グリル/東京都の鍋、グリル/新宿区の鍋、グリル/
            (投稿タイトル)                                    → 全8階層
```

「靴/バッグ」のように「カテゴリグループ」が1段多く挟まるカテゴリでは、
県名を期待していたposition(5)に実際にはまだカテゴリ名（「ブーツ」）が
入っており、`prefecture`の抽出に失敗していた。

**修正内容**：position番号の決め打ちをやめ、「投稿タイトルを除いた
末尾からの相対位置」で判定する方式に変更した。末尾から2番目が
「{都道府県}の{カテゴリ}」、3番目が最も詳細なカテゴリ名、4番目が
その親カテゴリ名、という並びはカテゴリの階層数によらず共通して
成り立つため、どのカテゴリでも安定して抽出できる。

### バグ修正3：評価0件のユーザーは`rating`が取得できない

**症状**：一度も評価が付いていない出品者の`rating`・`rating_count`が
常に`null`になり、「未評価」なのか「取得に失敗した」のか区別できない。

**原因**：投稿者ブロックの正規表現`r"(\d\.\d)\s*\((\d+)\)"`は
「5.0 (548)」のような件数付き表示を前提としていたが、評価が1件も
付いていないユーザーは「0.0」単体（件数の括弧書きなし）で表示される。

**修正内容**：件数付きパターンが一致しない場合、`0.0`単体パターンを
フォールバックとして試し、`rating=0.0, rating_count=0`として
明示的に保存するようにした。

### バグ修正4：新規投稿の初回巡回で、中間カテゴリ単位のNGカテゴリ登録が効かない

**症状**：中間カテゴリ（`category_mid_id`）だけをNGカテゴリ登録
していた場合、該当する新規投稿の初回巡回時にはNG判定されず、
フィルタにも通知抑制にも反映されない。

**原因**：`scheduler/job.py`の`run_scan`が、NGカテゴリ判定
（`check_ng_category`）を個別ページ取得より**前**に行っており、
一覧由来の`article.category_id`のみを渡していた。しかし
`category_mid_id`（中間カテゴリID）は個別ページ取得後にしか判明しない
（`filters/category_filter.py`のdocstring参照）。このため、新規投稿の
初回巡回時には`category_mid_id`が未確定のまま判定されてしまい、
中間カテゴリ単位のNG登録が初回巡回に限って効かなかった
（`filters/recompute.py`側は`category_mid_id`も見て判定するため、
NGルール変更後の再計算では正しく隠れる）。

**修正内容**：NGカテゴリ判定を個別ページ取得（`category_mid_id`確定）
の**後**に行うよう順序を入れ替えた。個別ページ取得が行われない既存
投稿の場合も、DBに保存済みの`category_mid_id`を都度読み直してから
判定するようにし、新規・既存どちらの経路でも同じ基準で判定される
ようにした。

### 新機能1：取得範囲設定（ページ数 or 過去n日、排他選択）

これまで一覧巡回は常に1ページ目のみに固定されていたが、設定で
「何ページ目まで」または「過去何日分まで」を選べるようにした
（排他選択。デフォルトはページ数指定・1ページ＝従来通りの挙動）。

**設計のポイント**：

- `scheduler/job.py`の`run_scan`（1ページ版、後方互換のため維持）を、
  「1ページ分の取得と記事単位のフロー処理」を担う内部関数
  `_scan_one_page`と、それを束ねる関数に分割した。理由：
  `mark_missing_articles`は「今回の巡回全体で見た全article_idの集合」
  を前提にしているため、単純に`run_scan`を複数回呼ぶと、2ページ目の
  呼び出し時に1ページ目の`seen_ids`が失われ、1ページ目にしか出現
  しなかった投稿が誤ってmissing化されてしまう。新設した
  `run_scan_with_range`は全ページの取得が終わってから1回だけ
  missing化・purgeを行う。
- 「過去n日」モードでは、一覧が新着順に並んでいる前提を利用し、
  各ページで最も古かった投稿の基準日（更新日があれば更新日、
  なければ作成日）が指定日数を下回った時点でページ送りを打ち切る。
- 重複投稿（既にDBにある投稿）は価格・タイトルの差分確認のみを行い、
  個別ページへは再アクセスしない（既存の`upsert_from_list_article`の
  挙動をそのまま踏襲）。このため取得範囲を広げてもアクセス数が
  跳ね上がるのは「新規に見つかった投稿の件数」に比例する分のみ。
- 設定は`db/schema.sql`の`scan_state`テーブルに`scan_range_mode`
  （`pages`|`days`）・`scan_range_value`として保存する。現時点では
  「複数の監視対象を切り替える」UIがまだ無いため、アプリ全体で
  共有する単一の設定として扱う
  （`repository/scan_settings_repository.py`）。
- バックエンドAPI：`GET/PUT /api/settings/scan-range`。
  `POST /api/scan`は保存済みの設定を読んで`run_scan_with_range`を
  呼ぶよう変更した。
- フロントエンド：設定画面（`SettingsPage.jsx`）に「取得範囲」タブを
  新設し、ページ数/日数の排他選択UIを実装した。

あわせて、将来の「自動更新頻度」機能のための設定項目の器
（`scan_state.auto_scan_interval_minutes`、設定画面の入力欄）も
用意した。2026-09-09に`scheduler/auto_refresh.py`として定期実行の
仕組み自体を実装し、設定した間隔で実際にサーバー側から自動巡回する
ようになった（詳細は後述の「新機能：自動更新のサーバー側定期実行」
セクション参照）。

### 新機能2：タイトル変更の反映（履歴は持たず最新値に上書き）

ジモティーの運用上、既存投稿のタイトルが「引取が決まりました！○○」
「最終値下げ！○○」のように後から書き換えられることがある。

2026-08-23時点の合意事項では「タイトル変更は追跡しない」としていたが、
今回のユーザーとの合意により方針を変更し、価格と同様に一覧巡回の
たびにタイトルの差分を確認し、変化があれば`active_articles.list_title`
を最新値に上書きするようにした。ただし価格ほど重要ではないという
判断から、`price_history`のような変遷の履歴テーブルは持たない
（個別ページへの再アクセスも発生しない。一覧のタイトル文字列同士を
比較するだけ）。変更が起きたこと自体は`title_changed_at`列に記録し、
将来UIで軽い変更表示（バッジ等）に使えるようにしてある。
`scheduler/job.py`側ではログレベルで変更を記録する。

### 新機能3（設計のみ）：都道府県・市区町村・マイエリアの選択に向けた地域指定の拡張

公式サイトの地域指定は「都道府県のみ」「都道府県＋市区町村（例：
新宿区まで、区は含まない）」「マイエリア（地図上の地点＋距離
1/2/5/10/30km）」の3方式があり、ユーザーから提供された実HTML
（`area_portal/{id}`ページ）で以下を確認した：

- `area_portal/{id}`はURLに都道府県・市区町村より細かい「地区ID」を
  持つが、都道府県・市区町村の構造化データ（BreadcrumbList等）は
  持たず、地域名は`<h1>`の自然文からのみ取得できる。
- 距離（1/2/5/10/30km）はURLパラメータではなく、`method=post`の
  フォーム（`area_portal/search`、フィールド名`distance`）で送信され、
  現在選択中の距離は`checked`属性を持つラジオボタンからHTMLで
  確認できる。
- カテゴリの絞り込みも同様にチェックボックス（`category_group_ids[]`）
  の`checked`有無で判定できる。
- ページ送りは`area_portal/{id}?page=N`という、通常のカテゴリ一覧
  ページ（`/p-N`形式、パスセグメント）とは異なるクエリパラメータ形式。
  【2026-09-07訂正】通常のカテゴリ一覧ページのページ送りは、当初
  `?p-N`（クエリパラメータ）と誤って記載していたが、実データ検証の
  結果`/p-N`（パスセグメント）が正しい形式だった
  （`scraper/fetch.py`の`build_list_url()`参照）。将来この
  `area_portal`対応を実装する際は、この誤った旧形式と混同しないこと。
- 投稿一覧アイテム自体のHTML構造（`p-articles-list-item`等）は
  通常のカテゴリ一覧ページと共通しており、`scraper/list_parser.py`の
  解析ロジックはそのまま再利用できる見込み。

これらの調査結果を踏まえ、`scan_state`テーブルに`region_type`
（`prefecture`|`prefecture_city`|`my_area`）、`area_portal_id`、
`distance_km`の列を追加し、将来の拡張に備えた。ただし「POSTで距離を
確定させた後、セッションを保ったまま2ページ目以降をGETで取得できるか」

`fetch_area_portal()`（距離・カテゴリの絞り込みPOSTのみ対応、
以前のセッションで実装済み）は、今回の実HTML調査の結果と整合して
いることを確認した。

### DBマイグレーションについて

`db/schema.sql`は`CREATE TABLE IF NOT EXISTS`で読み込まれる方式のため、
既に運用中のDBファイルには列追加が自動反映されない。このため
`repository/article_repository.py`の`get_connection()`に、起動時に
`ALTER TABLE ... ADD COLUMN`を試み、「既に列がある」エラーは無視する
軽量なマイグレーション処理を追加した（`scan_state`・`active_articles`
の両テーブルが対象）。新規DB・既存DBのどちらでも同じ結果になることを
確認済み。

### 新機能：自動更新のサーバー側定期実行（2026-09-09）

設定画面「自動更新」タブで指定した分数ごとに、`run_scan_with_range()`
を自動的に実行するようになった。ユーザー方針により、ブラウザを閉じて
いてもサーバープロセス（uvicorn）が起動している限り動作する
「サーバー側定期実行」方式を採用した。

- `scheduler/auto_refresh.py`を新設。外部スケジューラライブラリ
  （APScheduler等）は追加せず、標準ライブラリの`asyncio`のみで実装
  した。ローカル常駐のシングルユーザー向けツールという性質上、
  複雑なスケジュール指定は不要であり、依存を増やすデメリットの方が
  大きいと判断した。
- 30秒おきにDBをチェックし、「前回巡回（`scan_state.last_scanned_at`）
  からauto_scan_interval_minutes分以上経過したか」を判定して、経過
  していれば1回巡回する。`auto_scan_interval_minutes`が未設定
  （`None`）なら何もしない。
- FastAPIの`lifespan`イベント（`api/main.py`）でこのループを起動・
  終了する。`uvicorn api.main:app`での実起動を確認済み。

あわせて、この機能を実装する過程で2つの既存の問題を修正した。

- **`POST /api/scan`が常に固定の地域（東京都新宿区）で実行されていた
  問題**：引数のデフォルト値がハードコードされており、`scan_state`
  テーブルに保存されているはずの監視対象を一切参照していなかった。
  `repository.scan_settings_repository.get_monitored_target()`を新設し、
  リクエストに引数が明示されない場合はDBから監視対象を読むように
  変更した（引数が明示された場合は後方互換のためそちらを優先する）。
  現時点では地域変更UIはまだ無いが、将来UIを追加した際にこの
  仕組みがそのまま使えるよう、設定の置き場所（DB）だけを先に用意した
  （ユーザーとの合意事項）。
- **`scan_state.last_scanned_at`が一度も更新されていなかった問題**：
  列自体は以前から存在していたが、どこからも書き込まれていなかった。
  `run_scan_with_range()`の巡回完了時に`last_scanned_at`・
  `last_scan_item_count`を更新するようにした（手動実行・自動実行の
  両方で更新されるため、手動実行した直後に自動更新が重複実行される
  こともない）。

対応する回帰テスト（`tests/test_auto_refresh.py`、

### 2026-09-15：更新ボタンの停止アニメーション統一・正規表現の区切り文字ヘルプ追加・通知機能（Discord/トースト/ブラウザ）の共通化

ユーザーとの打ち合わせを経て、以下3点を実装した。

#### 1. 更新ボタンの停止アニメーション統一

「今すぐ更新」ボタン（`BottomNav.jsx`の`ManualScanButton`）は、誤タップ
防止のため2026-09-14に「1回目タップで確認待ち状態(armed)になり、3秒
以内に2回目タップすると実行される」という2段階タップ方式を導入して
いた。しかし、これは更新の「開始」側だけの対応であり、更新「停止」側
は従来通り`confirm()`（ブラウザ標準の警告ダイアログ）のままだったため、
「開始と停止で確認の見た目・操作感が統一されていない」という指摘を
受けた。

これに対応するため、停止側も同じ2段階タップ方式に統一した。開始側の
armed（indigo色）とは別の`stopArmed`状態として管理し、停止確認中で
あることが一目で分かるよう警告色（`alert`色、既存のNG判定色と共通）で
表示する。アイコンも、回転するLoader2から静止した■（Square）に切り
替え、「止まっている」ことを視覚的に示す。`confirm()`は撤去した。

#### 2. 正規表現の区切り文字に関するヘルプテキスト追加

「検索」タブの「含めるワード（いずれか含む）」欄に、たとえば
`メタルラック　スチールラック`のように全角スペースで区切って入力すると、
これがOR検索にならない（`.*(メタルラック　スチールラック)`という、
スペースを挟んだ連続一致の正規表現になってしまう）という指摘を受けた。

原因は`frontend/src/utils/pickupSearch.js`の`parseWordsInput()`が、
区切り文字としてカンマ（`,`）・読点（`、`）のみに対応しており、スペース
（半角・全角）を区切り文字として扱っていなかったため。

対応方針について打ち合わせた結果、パースロジック自体（スペースを区切り
文字に追加する、Google検索のようなフレーズ検索`"..."`に対応する等）の
変更は行わず、**入力欄にヘルプテキストを追加するのみ**とした
（ユーザーとの合意事項）。`PickupSearchBuilder.jsx`の「含めるワード」
「除外するワード」欄それぞれに、カンマ・読点区切りでOR検索になる旨の
説明を追加した。

#### 3. 通知機能（Discord/トースト/ブラウザ）の共通化

これまでDiscord Webhook通知のみだった「検索タブの条件にヒットした
新着投稿の通知」機能に、アプリ内トースト通知とブラウザ通知（Web
Notifications API）を追加した。3種類の通知先は同じ通知条件（NGでない
新規投稿 かつ 検索タブの正規表現にマッチ）を共有し、設定画面
「設定＞巡回設定＞通知」タブ（`DiscordNotificationSettings.jsx`）で
それぞれ個別にON/OFFを保存できる。

**バックエンド**

- `discord_notification_settings`テーブルに`in_app_enabled`・
  `browser_enabled`列を追加（`repository/article_repository.py`の
  マイグレーション処理で既存DBにも反映）。テーブル名はDiscord専用と
  して設計された経緯を残すため変更していない。
- `repository/discord_notification_repository.py`の
  `update_discord_notification_settings()`を拡張し、3種類の通知トグルを
  個別に保存できるようにした。`in_app_enabled`・`browser_enabled`を
  省略した場合は既存値を維持する（部分更新への後方互換性）。
- `scheduler/scan_runner.py`の
  `_load_pickup_search_pattern_if_any_notification_enabled()`
  （旧`_load_pickup_search_pattern_if_discord_enabled()`から改名）が、
  Discord・トースト・ブラウザのいずれか1つでも有効なら検索タブの
  正規表現を読み込むように変更。全て無効なユーザーには従来通り一切
  オーバーヘッドが生じない。
- `ScanResult`（`scheduler/scan_types.py`）に`pickup_search_matched`
  （検索条件にマッチした新規投稿のarticle_id一覧）を追加。
- 自動更新（サーバー側定期実行）はScanResultを誰にも返さずバック
  グラウンドで完結するため、手動・自動どちらの巡回結果もフロント
  エンドから参照できるよう、`scan_state`テーブルに
  `last_notified_article_ids`（JSON配列文字列）・`last_notified_at`
  列を追加した。`run_scan`・`run_scan_with_range`は巡回完了のたびに
  （対象0件でも）これを洗い替えする
  （`repository/scan_settings_repository.py`の
  `update_last_notified_articles()`）。
- `GET /api/scan-status`のレスポンスに`notified_articles`（該当投稿の
  簡易情報一覧）・`notified_at`を追加。フロントエンドはポーリングの
  たびにこの値を見て、前回から`notified_at`が変化していれば「新しい
  巡回結果」と判断する。

**フロントエンド**

- `DiscordNotificationSettings.jsx`を拡張し、アプリ内トースト通知・
  ブラウザ通知のトグルを追加。ブラウザ通知をONにする際、まだ通知許可
  が下りていなければ`Notification.requestPermission()`を呼ぶ。許可が
  拒否されている場合や、ブラウザが通知APIに非対応の場合はその旨を
  案内する。
- `ScanStatusContext.jsx`のポーリング処理（`refreshStatus`）で、
  `notified_at`の変化を検知し、変化していれば（かつ初回ロード時では
  なければ）通知設定に応じてアプリ内トースト・ブラウザ通知を発火する。
  アプリ起動直後の初回ポーリングでは、過去の巡回結果を「新着」として
  誤通知しないようスキップする。
- 新規コンポーネント`ToastContainer.jsx`を追加し、`App.jsx`から
  `ScanStatusProvider`の内側に配置。画面上部にポップアップとして
  表示し、8秒後に自動で消える（×ボタンでも手動で閉じられる）。
- ブラウザ通知（`new Notification()`）はタブを開いている間のみ動作する
  設計とした（Service Worker・Push APIによるバックグラウンド配信は
  実装していない。iOS Safariでは通知許可自体がPWA化しないと出ない
  場合があるが、まずはブラウザでの利用を中心に考え、許容することで
  合意した）。

**既読管理は今回のスコープに含まれていない**（README「未実装」
セクション参照）。トースト自体は時間経過または手動操作で消えるのみで、
「どの通知を確認済みか」を記録する仕組みは無い。

**保留とした機能**：投稿の画像・タイトルから相場（メルカリ・Amazon等）
を検索するショートカット機能も打ち合わせで検討したが、実装コスト・
外部サービスの規約面（メルカリは公式APIなし、Amazon PA-APIは画像検索
非対応）を踏まえ、今回は見送り、将来の機能追加として保留することで
合意した。

## 本番運用化（2026-09-15）

### 背景

これまでの開発中の使い方は、`start.sh` / `start.bat`で
「Vite開発サーバー（フロントエンド、5173番ポート）」と
「uvicorn --reload（バックエンド、8000番ポート）」の2つを別々に起動する
構成だった。この構成はコード修正のたびに自動反映される（保存すれば
即座にブラウザに反映される）便利さがある一方、Vite開発サーバーは本来
「開発中に使うもの」であり、PCを常時起動しっぱなしで長期間動かし続ける
運用には向いていない。

このため、「ある程度開発が落ち着き、普段使いのツールとして安定的に
動かし続けたい」という段階向けに、**フロントエンドを一度だけビルド
（`npm run build`）し、その成果物をバックエンド（uvicorn）ひとつだけで
配信する**構成を追加した。以後、コードを修正しない限りはこの構成の
まま使い続けられる（＝細かい修正のたびに毎回ビルドし直す必要はない。
修正が入ったときだけ、開発側でビルドし直したものを反映すればよい）。

### 使い方

1. 初回のみ、依存関係をインストールする（開発時と同じ）:
   ```
   pip install -r requirements.txt
   cd frontend && npm install && cd ..
   ```
2. 本番用の起動スクリプトを実行する:
   - Mac/Linux: `./start_production.sh`
   - Windows: `start_production.bat`をダブルクリック

このスクリプトは、
   1. フロントエンドをビルドする（`frontend/dist/`に静的ファイル一式を生成）
   2. `uvicorn api.main:app --host 0.0.0.0 --port 8000`を起動する

を自動的に行う。起動後、このPC自身からは`http://localhost:8000`、
同じ家のLAN内にある他の端末（スマホ等）からは、スクリプト実行時に
画面へ表示されるIPアドレスを使って`http://<IPアドレス>:8000`で
アクセスできる（インターネットには公開されない。外部からのアクセスは
できない）。

終了する場合は、開いているターミナル（Windowsの場合はコマンド
プロンプトの黒い画面）で`Ctrl+C`を押すか、ウィンドウを閉じる。

### 自動起動について

「PCを再起動したときに自動でこのアプリも起動してほしい」という場合、
上記の`start_production.sh` / `start_production.bat`を、OSのスタート
アップ登録・タスクスケジューラ等に登録する方法がある（具体的な登録
手順はOS・環境によって異なるため、このREADMEでは扱わない）。

### コードを修正した場合

開発用の`start.sh`と異なり、この本番運用構成は**保存しただけでは
自動反映されない**（意図しない再起動によって巡回中の処理が中断される
ことを避けるため、あえて自動リロードを行わない設計にしている）。
コードを修正した場合は、

1. 起動中のスクリプトを一度終了する（`Ctrl+C`）
2. 再度`start_production.sh` / `start_production.bat`を実行する
   （スクリプトの中でビルドをやり直すので、修正が反映される）

という手順を踏む必要がある。

### 技術的な変更点

- `api/main.py`：`frontend/dist/`が存在する場合のみ、これを配信する
  ルートを末尾に追加した（`StaticFiles`で`/assets/...`を、キャッチ
  オールルートで`index.html`へのSPAフォールバックを行う）。
  `frontend/dist/`が存在しない場合（＝ビルドしていない、開発時の
  通常状態）は何も変わらず、従来通りVite側でフロントエンドを配信する
  前提のまま動作する。
- `frontend/src/api/client.js`：APIの接続先（`BASE_URL`）を、開発時は
  従来通り`http://localhost:8000/api`、本番ビルド時は相対パス`/api`を
  使うように変更した。これにより、`http://<PCのIPアドレス>:8000`で
  アクセスした場合でも、正しく同じホストのAPIを呼び出せるようになる
  （固定のlocalhostのままだと、スマホ等からアクセスした際に
  「スマホ自身のlocalhost」を指してしまいAPIに繋がらなかった）。
- `start_production.sh` / `start_production.bat`：本番運用向けの
  起動スクリプトを新設（上記「使い方」参照）。
- `tests/test_static_file_serving.py`：静的ファイル配信・SPAフォール
  バック・既存APIルートとの共存を検証するテストを新設（7件）。
