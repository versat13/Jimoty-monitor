# ジモティー新着監視ツール

ジモティー（jmty.jp）の指定エリア・カテゴリを定期巡回し、新着投稿の検知・
価格変動の追跡・NGワード/NGユーザーによるフィルタリングを行う自己ホスト型
の監視ツールです。バックエンド（FastAPI + SQLite）とフロントエンド
（React + Vite）から構成されます。

> **本ツールはジモティーの非公式ツールです。** サイトから情報を自動取得
> する仕組みを含むため、利用にあたってはジモティーの利用規約・robots.txt・
> 関連法令を利用者ご自身の責任でご確認・順守してください。本READMEは
> 規約適合性について何も保証するものではありません。
>
> 参考として、デフォルト設定（30分間隔・1ページのみ巡回）における
> 1回の巡回のアクセス量は「一覧ページ1回 + 新規投稿があった場合のみ
> その個別ページ」で、人が手動でジモティーを開いて新着を確認する頻度・
> 量とおおむね同程度になるよう意図しています。とはいえ「量が少なければ
> 規約上問題ない」とは限らないため、自動化されたアクセス自体を制限する
> 記載が規約にないか、利用前に必ずご自身で確認してください。取得範囲を
> 広げる（ページ数を増やす、間隔を短くする）ほどアクセス量は増えるため、
> 変更する場合は特に注意してください。

## できること

- 指定した都道府県・市区町村・カテゴリの一覧ページを一定間隔で自動巡回
- 新着投稿の検知、既存投稿の価格変動・タイトル変更の追跡
- NGワード／NGカテゴリ／NGユーザー（出品者単位）によるフィルタリング
  （フィルタで弾いた投稿も削除はせず「NG」タブで後から確認可能）
- ウォッチリスト（投稿単位・出品者単位）
- Discordへの新着通知
- 一覧に出なくなった投稿を「終了」タブで確認（誤って削除しない設計）
- 表形式／カード形式でのUI表示、公式サイトと同じ並び順（おすすめ順）表示

## セットアップ

### 必要環境

- Python 3.11以上
- Node.js 20以上

### 手順

```bash
# 1. リポジトリを取得
git clone <このリポジトリのURL>
cd jimoty-monitor

# 2. バックエンドの依存パッケージをインストール
pip install -r requirements.txt

# 3. ユニットテストで動作確認（513件、すべて通過するはず）
python3 -m pytest tests/ -v

# 4. 巡回ジョブを1回実行し、DB（jimoty_monitor.db）を作成
python scripts/run_scan_once.py

# 5. バックエンドAPIを起動
uvicorn api.main:app --reload --port 8000

# 6. フロントエンドを起動（別ターミナルで）
cd frontend
npm install
npm run dev
```

5・6を両方起動した状態で `http://localhost:5173` を開くと、取得した
投稿一覧やフィルタ設定をUIから操作できます。

**まとめて起動したい場合**は、直下の`start.sh`（Mac/Linux）または
`start.bat`（Windows）を使うと、バックエンド・フロントエンドを1回の
実行でまとめて起動できます（初回は事前に上記2・6の`install`が必要）。

```bash
chmod +x start.sh   # 初回のみ
./start.sh
```

### 監視対象の設定

初回起動後、UIの「設定」から巡回対象の都道府県・市区町村・カテゴリ、
巡回間隔、取得範囲（何ページ分／過去何日分）を設定してください。
デフォルトは低頻度アクセス（30分間隔・1ページのみ）になっています。

> **注意：** 取得範囲を「1ページのみ」にしていると、ジモティー側の
> 「おすすめ順」の変動によって投稿が1ページ目の外に押し出された場合、
> その投稿の並び順情報が更新されなくなり、実際の公式サイト上の順位より
> 上位に表示され続けることがあります（詳細は
> [Issues](../../issues)を参照）。取得範囲を2〜3ページに広げることで
> 追従しやすくなります。

## アーキテクチャ

```
scraper/     一覧・個別・プロフィールページのHTMLパーサー、HTTP取得
filters/     NGワード・NGカテゴリ・出品者ルールによるフィルタ判定
repository/  SQLiteへの読み書き（投稿・出品者・設定・履歴）
scheduler/   巡回ジョブ本体（一覧取得→パース→フィルタ→保存→通知を統合）
notifications/ Discord通知
api/         FastAPIによるバックエンドAPI
frontend/    React + Viteによる管理UI
db/          SQLiteスキーマ定義
tests/       ユニットテスト（513件）。tests/fixtures/に実データベースの検証用HTML
```

処理の大まかな流れ：

1. `scheduler`が`scraper`を使って一覧ページを取得・パース
2. `filters`でNGワード／NGカテゴリ／NGユーザーを判定（除外はせずフラグ付け）
3. `repository`経由でSQLiteに保存（新規投稿・価格変化・状態遷移を記録）
4. 新規投稿があれば`notifications`経由でDiscordに通知
5. `api`が`frontend`にデータを提供

より詳細な設計判断の経緯（実機検証で発見したバグとその対処など）は
[docs/DEVLOG.md](docs/DEVLOG.md)、HTML構造の解析結果は
[docs/HTML解析仕様_v1.1_追補版.md](docs/HTML解析仕様_v1.1_追補版.md)を参照してください。

## テスト

```bash
python3 -m pytest tests/ -v
```

513件のユニットテストがあり、うち多くは実際にジモティーから取得した
HTML（`tests/fixtures/`配下）を検証用データとして使用しています。
